## Fixed rules
- Never write client data (URLs, accounts, names, credentials) in this repository.
- Follow the hierarchy of sources of truth of the methodology (section 1.3).
- A project workspace always lives outside this repository, in qa-workspaces/.
- Before any change to the framework, follow the validation process (methodology section 15).
- Everything in this repository is in English (plan 8.11); a project's own names (sheets, columns, statuses) are never translated.

## Scripts (from the root of qa-assistant)
- `python scripts/validate_project.py <workspace> [--environment [--strict] [--ci]]` — (`--ci` on a runner of the workspace's CI: `.env` needs only the names of `ci.secrets`) validates `project.yaml` (environments, modules, sections, URLs inside the environments, Excel, the `jira:` / `azure_devops:` section, the optional `ci:` section of remote execution — standard runner only, limits, `ci.secrets` names, login mode and helper flow —, dashboard; warns if `.env` and the like are not in `.gitignore`; in a workspace with its own git: no remote, commits not pushed, `.env.example` missing a variable, files over 50 MB are warnings, `.env` tracked or a public remote are problems); `--environment` also checks this computer, `[ok|missing] <tool>: …` (git, Python, `.env` has every name — never a value —, skills in sync; LibreOffice for `excel`, Node.js for browser modules, `qa-audit` and its browser for `accessibility`, Maestro/adb/emulator and `mobile.build.source` for `mobile`; resuming elsewhere: `docs/workspace/resume.md`); missing tools are warnings unless `--strict`; 0 ok · 1 problems (or a missing tool with `--strict`)
- `python scripts/workspace_git.py <workspace> init|status|remote --create OWNER/NAME [--yes]|remote --set URL|push [--i-confirm-private]` — the workspace as a git repository of its own with a private remote: `init` (branch main, `.gitignore` from `docs/workspace/gitignore`, `.env.example` with the variable names, initial commit; idempotent), `status` (branch, remote, commits not pushed, untracked, files over 50 MB, visibility through `gh`), `remote --create` (prints the `gh repo create … --private` and runs it only with `--yes`), `push` (never `--force`; refused for a public or unconfirmed remote, `.env` tracked or a file over 50 MB); 0 ok · 1 refused · 2 usage/configuration · 3 git/gh failed
- `python scripts/migrate_workspace.py <workspace> [--apply]` — converts a workspace from before the translation (plan 8.11) to the English names and keys; dry run without `--apply`; 0 converted or nothing to do · 1 changes to make · 2 refused
- `python -m adapters.excel.inspect <copy.xlsx>` — proposes the `excel:` section (onboarding)
- `python -m adapters.excel.apply <workspace> <batch.json>` — applies a batch to the workbook (0 ok · 2 cross-check · 3 recalculation · 4 invalid batch · 5 summary does not match)
- `python -m adapters.tracker <workspace> check|import-cases [--query …]|export-cases <cases.json> [--yes]|apply <batch.json> [--yes] [--now …]|bug-search <draft.json> [--include-closed]` (+ `--record`) — the Jira (Xray) / Azure DevOps tracker adapter, the tracker from `project.yaml` (technique-jira-xray.md §2): writing commands are a dry run without `--yes`; record of what was sent in `tracker/sent/`, ID cache `tracker/ids.yaml`, imported cases `tracker/cases.json`; the run log needs the `run` block. **Jira Cloud + Xray Cloud is built (plan 10.2)**: `check` (project, issue types, fields on the create screens, bug statuses, link type, test plan, Xray statuses), `import-cases` (JQL + Xray steps, flags), `export-cases` (Xray `createTest`, marker label, test plan), `apply` (new bugs, one Test Execution per batch through the Xray import in chunks of 100, comments, `bug_status` transitions, links, evidence only with `text+screenshot`, read back), `bug-search` (JQL with relaxed passes, candidates only). **Azure DevOps Services is built (plan 10.3)**, PAT, api-version 7.1: `check` (process Agile/Scrum — Basic refused, CMMI not covered —, work item types, fields, bug states, test plan and suites, Test Configurations), `import-cases` (the plan's suites or `--query` WIQL, `workitemsbatch`, steps XML, shared steps expanded and flagged, test points and their latest outcome), `export-cases` (`$Test Case` with the steps XML, tag marker, added to `new_cases_suite_id`), `apply` (new bugs Tested By the case, `bug_status` with a `test` on `/rev`, one test run per batch on the test points — platform → `results.configurations` —, outcomes and bugs on the results, evidence only with `text+screenshot`, comments on existing bugs, read back), `bug-search` (WIQL with relaxed passes); 0 ok or nothing to send · 1 dry run, not approved yet · 2 conflict with the tracker · 3 network/auth/rate limit (a send may be partial; run again to continue) · 4 invalid input/configuration (incl. `Question`) · 5 read back differs
- `python scripts/api_request.py <workspace> <METHOD> <path> …` — one HTTP request with redacted evidence (0 ok · 1 different code · 2 usage · 3 no response)
- `python scripts/audit_a11y.py <workspace> [--output …]` — accessibility of the pages of `project.yaml` through the `qa-audit` engine (axe-core, keyboard, reflow; 0 ok · 2 configuration/engine · 3 page not audited); needs the engine installed (`pip install -e .`, `qa-audit doctor`)
- `python scripts/run_mobile.py <workspace> [flows…] [--output …]` — runs the Maestro flows and links them to the cases; each flow is a path or the case ID (0 ok · 2 configuration or missing flow · 3 no target); `--helper flows/_<name>.yaml [--serial S]` runs one helper flow that is not a case (e.g. asking for a login link with `${MAESTRO_<VAR>}` from `.env`), output redacted, no result recorded (0 passed · 2 configuration · 3 failed or no target)
- `python scripts/run_log.py <workspace> add <batch> <case> <status> <actual> [--bug ID] [--new-defect FILE] [--evidence …] [--environment E --build B]` — appends or replaces one case's result in `runs/batch_<batch>.json` (the project's vocabulary or `Question`; the `run` block); refuses a batch already applied (the workbook's control sheet, or `tracker/sent/`) and names a new batch for the correction (0 written · 1 refused · 2 usage)
- `python scripts/device.py <workspace> [--serial S] check|dump|tap|type|send|shot|link …` — drives an Android device/emulator through `adb` for the conversational mode (screen text with bounds, tap by text, Unicode typing through Maestro — `type`/`send --file <utf8.txt>`, text in chunks of 300 characters, Maestro's "IME is not active" retried once then ASCII through `adb`, `type --via adb|maestro` —, send and wait for the answer to settle, screenshots to `evidence/<batch>/`, deep links never printed); only with `mobile.app_id` in the foreground (0 ok · 2 usage/configuration · 3 no target, app not in the foreground or timeout · 4 element not found)
- `python scripts/workspace_build.py <workspace> publish <app.apk> [--yes] [--allow-prod] [--i-confirm-private]|fetch [--tag T] [--dest app]` — the app's builds as releases of the workspace's private repository (plan 11.1): `publish` reads package, versionName and versionCode from the APK's binary manifest in pure Python (`scripts/apk_manifest.py`, no aapt2), prints what it would do without `--yes`; with `--yes` creates the release `build-<versionName>-<versionCode>` (the APK as asset, the SHA-256 in the notes), sets `mobile.build` (`source: release <tag>`, `sha256`, `version`; the file's comments kept) and commits `project.yaml` (never pushes); refuses another package, a production build, a public/internal (or unconfirmed) repository and a tag that exists with another hash. `fetch` downloads the release's APK to `app/<tag>.apk` and checks its SHA-256 (`mobile.build.sha256`, or the release's notes for another `--tag`), `apk=` to `$GITHUB_OUTPUT` on a runner; 0 ok or dry run · 1 refused · 2 usage/configuration · 3 gh/git failed
- `python scripts/workspace_ci.py <workspace> install [--yes] [--i-confirm-private]|check [--batch NAME]` — the workspace's CI, remote execution on a GitHub Actions runner (plan 11.4, technique-mobile.md §11, settings in `docs/workspace/ci/README.md`): `install` copies the templates of `docs/workspace/ci/` into the workspace's `.github/` (nothing of the project in them: they read `project.yaml`), lists the secrets (`CLAUDE_CODE_OAUTH_TOKEN`, `QA_ASSISTANT_TOKEN`, `ci.secrets`) and which exist, refuses a repository that is not private; dry run without `--yes`; with `--yes` copies, sets the variable `QA_ASSISTANT_REPOSITORY` and, in a terminal, runs `gh secret set NAME` for each missing one (the user types the value; never on a command line); `check` validates the installed copies, the secrets, `ci:`, the flows, the login's helper flow, `mobile.build` as a release and `--batch` (a planned `batches/<name>.yaml` or case IDs), and warns about the Actions spending limit / minutes when the billing API answers — a dry run without `act`. The workflow's own steps: `batch`, `blocked`, `import-flows` and `write-env` (it writes `.env` from the Actions secrets it is given, only the names of `ci.secrets`); 0 ok · 1 problems/refused · 2 usage · 3 gh failed
- `python scripts/remote_login.py <workspace> request|wait [--run-id ID] [--serial S] [--interval 15]` — the manual login of a remote run through an issue (plan 11.3, technique-mobile.md §11.2): `request` runs the helper flow `ci.login.flow` and opens (or reuses) the issue "Login needed — <run id>" mentioning `ci.login.user` (default the repository's owner); `wait` polls its comments every 15 s up to `ci.login.timeout_minutes`, uses only that user's comment with a URL of a host of `environments` / `ci.login.hosts`, masks it (`::add-mask::`), opens it in-process (`device.open_link`), deletes the comment, closes the issue and checks the app left `ci.login.screen_text`; other comments ignored and reported without their text; the URL never in a file, log line, comment or PR (0 logged in or `mode: none` · 2 configuration · 3 Blocked (login): helper failed, timeout, not opened, still on the login screen)
- `python scripts/setup_emulator.py <workspace> [--avd NAME] [--image …] [--apk PATH] [--no-boot] [--no-audio] [--cold] [--gpu MODE] [--headless] [--allow-prod] [--dry-run]` — prepares a reproducible Android emulator, idempotent: SDK, AVD, boot (cold — `-no-snapshot-load` — with `--cold` or when the AVD's saved snapshot is older than the build; `--gpu swiftshader_indirect --headless` on a runner), the build checked against `mobile.build.sha256` (installed only when the versionCode differs, read from the APK's manifest without aapt2), ARM-only native libraries on an x86_64 image (root image), `mobile.permissions`, Chrome's first run off; refuses production builds (0 ok · 2 configuration, SHA-256 mismatch or production build · 3 did not boot or a device step failed)
- `python scripts/build_dashboard.py <workspace> [--open]` — builds (and opens) the workspace's `dashboard.html`; it is what `/dashboard` runs
- `python scripts/sync_skills.py [--apply]` — compares (and copies) `.claude/skills/` with `~/.claude/skills/`, the copy the workspaces use; run with `--apply` after changing a skill (0 in sync · 1 differences); also removes the old skill names
- `qa-audit <url> [--type accessibility,security,performance,functional,visual] [--sitemap] [--browser chromium,firefox,webkit|all] [--allow-submit] [--update-baseline]`; `qa-audit baselines [--delete HOST] [--browser …]`; `qa-audit login <url> --config FILE` (saves a session for `auth.method: storage-state`) and `qa-audit sessions [--delete HOST]`; `qa-audit check --cdp URL --page-url REGEX --label NAME` (audits the page an N2 spec has open; helper `integrations/playwright/qa-audit.ts`) — automated audit of any site (`pip install -e .` first); `qa-audit doctor` checks the environment (docs/qa-audit.md). Engine integration tests: `python -m unittest discover -s tests/integration` (browsers must be able to start: outside the Bash sandbox)
- `python scripts/update_axe.py <version>` — updates the axe-core bundled with `qa-audit` (npm integrity checked)
- Tests: `python -m unittest discover -s tests` and `python scripts/golden_check.py` (needs LibreOffice); a workspace's real golden: `python scripts/golden_check.py --dir <workspace>/golden/<batch>` (methodology §15)
